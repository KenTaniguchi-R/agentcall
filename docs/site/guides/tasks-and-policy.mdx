---
title: Tasks and policy
description: Publish narrow AgentCall tasks, set what each caller may be told, and test the effective policy.
---

Tasks define what an answering agent is asked to do. Policy defines how much of
what it finds may reach each caller.

## 1. Scaffold a task

```bash
agentcall task new architecture-history
```

Edit `~/AgentCall/<line>/tasks/architecture-history/SKILL.md`:

```yaml
---
description: Explain why past architecture decisions were made.
keywords: [architecture, migration, adr]
workdir: /absolute/path/to/the/repository
---

Use ADRs, commit history, and current code to explain the decision.
Call out uncertainty instead of inventing rationale.
```

Only `description` is required. Optional fields are `name`, `keywords`,
`examples`, `timeout_s`, `workdir`, and `threadable`. The directory name is the
task ID. Unrecognized keys are rejected rather than ignored, so a stale field is
a startup error and not a silent no-op.

## 2. Validate before publishing

```bash
agentcall lint
agentcall policy
agentcall card
```

`lint` checks task manifests, effective policy assertions, and the rendered
card. The other commands make the effective clearances and working directories
visible for human review.

## 3. Set clearance

Any caller you have not blocked can request any task. What bounds the answer is
what the task read, not which task ran: every source carries a **sensitivity**
(`public`, `internal`, `secret`), every caller a **clearance**, and the reply is
refused unless the running context sits at or below that clearance.

```bash
# What anyone in the organization may be told
agentcall clearance --default public

# One caller may be told more
agentcall clearance ken internal

# Back to the line default
agentcall clearance ken --reset

# Deny a caller completely — beats every grant, including a roster's
agentcall block spammer
```

`secret` is not grantable. It means "never leaves this machine", so no caller
and no roster can be cleared for it.

Policy verbs republish the card automatically. `agentcall card push` republishes
after a direct policy-file edit.

## Add policy assertions

Assertions prevent an accidental edit from silently widening access. Each pins
the clearance one caller resolves to, which is the value that actually governs
what leaves:

```json
{
  "default_clearance": "public",
  "callers": {
    "ken": { "clearance": "internal" },
    "stranger": { "block": true }
  },
  "groups": {
    "eng": { "roster_id": "<relay-issued roster id>", "clearance": "internal" }
  },
  "tests": [
    { "caller": "ken", "expect_clearance": "internal" },
    { "caller": "stranger", "expect_clearance": "blocked" },
    { "caller": "someone-else", "groups": ["eng"], "expect_clearance": "internal" }
  ]
}
```

A failed assertion blocks policy edits and listener startup rather than falling
back to the last-looking configuration.

<Warning>
  Anything absent from `sensitivity.json` is `secret` and never leaves — but the
  reverse is the real risk: labelling a parent directory `internal` labels
  everything beneath it, including anything a subdirectory later acquires.
  Codex cannot enforce the same file-read boundary as Claude, so on a Codex line
  the clearance check on the reply is what bounds what leaves. Review the
  [security model](/security/overview) before widening a label.
</Warning>

## Success check

`agentcall lint` exits successfully and `agentcall card` shows the intended
tasks, the default clearance, and each named caller's resolved level—nothing
more.
