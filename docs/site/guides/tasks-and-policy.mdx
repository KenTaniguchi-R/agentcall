---
title: Tasks and policy
description: Publish narrow AgentCall tasks, set what each caller may be told, and test the effective policy.
---

Tasks define what an answering agent is asked to do. Policy defines how much of
what it finds may reach each caller.

## 1. Scaffold a task

```bash
agentcall task new architecture-history
```

Edit `~/AgentCall/<line>/tasks/architecture-history/SKILL.md`:

```yaml
---
description: Explain why past architecture decisions were made.
keywords: [architecture, migration, adr]
---

Use ADRs, commit history, and current code to explain the decision.
Call out uncertainty instead of inventing rationale.
```

Only `description` is required. Optional fields are `name`, `keywords`,
`examples`, `timeout_s`, and `threadable`. The directory name is the
task ID. Unrecognized keys are rejected rather than ignored, so a stale field is
a startup error and not a silent no-op.

## 2. Validate before publishing

```bash
agentcall lint
agentcall policy
agentcall card
```

`lint` checks task manifests, effective policy assertions, and the rendered
card. The other commands make the effective access rules and working directories
visible for human review.

## 3. Decide who is answered

Any caller you have not blocked can request any task. What bounds the answer is
what the task read, not which task ran: a path outside every root, or on the
denylist, is refused **at the read** — before the agent sees it. The answer
itself is not inspected.

<Warning>
  **This does not bound `Bash`.** A caller can reach any file on the machine
  through a shell command; the guard records it and allows it, because a command
  string cannot be inspected for what it will read. The roots and the denylist
  shape what the agent reaches by default — they are not a boundary against a
  caller who asks for something else. See
  [#419](https://github.com/KenTaniguchi-R/agentcall/issues/419).
</Warning>

Who gets answered is a separate, yes/no question. **Everyone answered sees the
same thing** — the organization is the boundary, not a per-caller level.

```bash
# Deny a caller completely — beats the default and every roster rule
agentcall block spammer
agentcall unblock spammer

# Answer only named callers and attested rosters
agentcall access --default blocked
```

`secret` is not grantable. It means "never leaves this machine", so no caller
and no roster can reach it.

Policy verbs republish the card automatically. `agentcall card push` republishes
after a direct policy-file edit.

## Add policy assertions

Assertions prevent an accidental edit from silently widening access. Each pins
whether one caller is answered, which is what actually governs whether anything
leaves:

```json
{
  "default_access": "blocked",
  "callers": {
    "ken": { "access": "allowed" },
    "stranger": { "access": "blocked" }
  },
  "groups": {
    "eng": { "roster_id": "<relay-issued roster id>", "access": "allowed" }
  },
  "tests": [
    { "caller": "ken", "expect_access": "allowed" },
    { "caller": "stranger", "expect_access": "blocked" },
    { "caller": "someone-else", "groups": ["eng"], "expect_access": "allowed" }
  ]
}
```

A named caller wins over every roster, in both directions. Between two attested
rosters that disagree, **blocked wins** — the cautious direction when the
question is whether to answer at all.

A failed assertion blocks policy edits and listener startup rather than falling
back to the last-looking configuration.

<Warning>
  `scope.json` names a root the agent may read under, and a denylist that holds
  regardless. **A path you never thought about is readable** — the default root
  is `$HOME`, so anything a subdirectory later acquires is in scope too.
  **On a Codex line none of this is enforced.** There is no read guard there at
  all, so nothing stops a denied read, and nothing inspects the answer.
  Review the [security model](/security/overview) before widening a root.
</Warning>

## Success check

`agentcall lint` exits successfully and `agentcall card` shows the intended
tasks, the default access, and each named caller's resolved access—nothing
more.
