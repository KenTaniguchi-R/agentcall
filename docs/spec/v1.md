# AgentCall protocol, version 1

**Status:** Normative for the frames, lifecycle, error taxonomy, and limits it
covers. Incomplete by design — see [What this version does not
specify](#what-this-version-does-not-specify). Sections not yet written are
absent rather than approximated.

**Relationship to the code.** `packages/shared/src/protocol.ts` and
`packages/shared/src/e2ee.ts` are the machine-checkable source for frame
*shape*. This document is the source for everything a schema cannot express:
ordering, obligations, terminal states, idempotency, and what an implementation
is forbidden from doing. Where the two disagree about shape, the schema wins and
this document is a bug. Where this document states an obligation the schema
cannot encode, this document is the contract.

`apps/relay` is **not** normative. It is one implementation. A self-hosted relay
conforms by satisfying this document, not by matching that code.

## Conventions

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are to be interpreted
as described in RFC 2119.

"Caller" is the party initiating a call. "Callee" is the party whose agent runs.
"Relay" is the intermediary. "Listener" is the callee's long-lived connection to
the relay.

## Addressing

An address is `@org/handle`. Both components are constrained by `ADDRESS_RE` in
`protocol.ts`.

- The organization is the outermost routing boundary. A relay MUST NOT route a
  call between two organizations, and MUST NOT expose a discovery surface that
  reveals whether a handle exists in another organization.
- A human belongs to exactly one organization. This is a permanent design
  decision, recorded in
  [the federation non-goal](../superpowers/specs/2026-08-02-cross-organization-federation-non-goal.md).
- The address names no host. A verifier that needs the scoping host MUST read
  `relay_origin` from the signed key record rather than parsing it out of the
  address.
- The historical `handle@host` form MUST be rejected. It MUST NOT be accepted
  for compatibility.

## Transport and roles

A connection is a WebSocket to the relay carrying a bearer credential. A
connection takes exactly one role for its lifetime: `call` or `listen`.

- A relay MUST authenticate every connection before admitting it to either role.
- A relay MUST reject a frame whose declared `from` does not match the
  authenticated identity on that connection.
- A listener MUST send periodic keepalives and a relay MAY close a connection
  that stops sending them. Keepalive cadence is a deployment choice.

## Frames

Frames are JSON. Every frame carries a `type` discriminator. The unions below
are exhaustive; a receiver MUST reject an unrecognized `type` rather than
ignoring it.

### Caller to relay

| Frame | Purpose |
|---|---|
| `call_request` | Initiate a call. Carries an HPKE envelope with `direction: "request"`. |
| `cancel_call` | Request cancellation of an in-flight call. |

`call_request` carries `correlation_id` (required), and `message_id` /
`delivery_mode` (`"sync"` or `"durable"`). **`message_id` MUST be present when
`delivery_mode` is `"durable"`**, and a relay MUST reject a durable request
without one.

### Relay to caller

| Frame | Purpose |
|---|---|
| `call_status` | Progress: `ringing`, `answered`, or `working`. Advisory. |
| `call_queued` | Durable receipt. The call was accepted into the mailbox, not answered. |
| `call_error` | Relay-originated failure. `origin` is always `"relay"`. |
| `call_outcome` | Terminal result, carrying a response envelope. |

### Relay to listener

| Frame | Purpose |
|---|---|
| `incoming_call` | A call to execute. Durable delivery additionally requires `message_id`, `lease_id`, and `execute_by`. |
| `cancel_call` | Cancellation request to relay onward to the running agent. |

### Listener to relay

| Frame | Purpose |
|---|---|
| `call_accepted` | The listener owns the call. It has not yet started an agent. |
| `call_started` | An agent process has started. |
| `call_outcome` | Terminal: `completed` or `failed`. |
| `call_cancelled` | Cancellation took effect, in phase `pending` or `running`. |
| `call_not_cancelled` | Cancellation did not apply: `already_terminal`, `unknown`, or `too_late`. |
| `call_rejected` | The frame was malformed. |

`call_accepted` and `call_started` are deliberately distinct. A relay MUST NOT
treat acceptance as process start: the split is what distinguishes "the frame
never arrived" from "the listener owns it but has not spawned yet", and a task
store MUST use it to separate `TASK_STATE_SUBMITTED` from working.

## Call lifecycle

### Synchronous delivery

1. Caller sends `call_request` with `delivery_mode: "sync"` (or omitted).
2. Relay authenticates, authorizes, and checks rate limits.
3. If no listener is connected, the relay MUST fail the call immediately with
   `offline`. It MUST NOT queue a synchronous call.
4. Relay forwards `incoming_call` to the listener and MAY emit `call_status`
   frames to the caller.
5. Listener replies `call_accepted`, then `call_started`, then `call_outcome`.
6. Relay forwards the outcome to the caller. The call is terminal.

The relay MUST bound the call by `RELAY_CALL_TIMEOUT_MS` and emit `timeout` if
it elapses. The callee's agent is separately bounded by `AGENT_TIMEOUT_MS`. The
relay bound MUST exceed the agent bound so a slow agent produces an agent-side
failure rather than a relay timeout.

### Durable delivery

Durable delivery is an **owner-enabled exception**, not a general queue.

1. A callee that has not enabled offline delivery MUST fail closed exactly as in
   the synchronous case. Enablement is the callee's decision alone.
2. On acceptance the relay returns `call_queued` — a receipt, not a reply. A
   caller MUST NOT treat `call_queued` as an answer.
3. The relay stores the request envelope as ciphertext. It MUST NOT be able to
   read it.
4. Delivery is attempted until `execute_by`. The relay MUST NOT extend that
   deadline on the caller's behalf.
5. On expiry the task becomes terminal with reason `expired`.

## Cancellation

A relay MUST NOT report a call as cancelled until the callee has confirmed that
the pending work was removed or the process group was observed exited.
Acknowledging on signal-sent would publish a cancelled call whose agent is still
running on the callee's machine.

If the callee cannot confirm, the relay MUST relay `call_not_cancelled` with its
reason rather than synthesizing a cancellation.

## Error taxonomy

Three enums exist because *who failed* is part of the contract. An
implementation MUST NOT collapse them.

**`RelayOperationalErrorCode`** — the relay failed or refused. Never reaches an
agent. `unknown_handle`, `offline`, `timeout`, `canceled`, `unauthorized`,
`rate_limited`, `message_too_large`, `protocol_error`, `busy`.

**`PeerFailureCode`** — the callee's side declined or failed, inside the
encrypted outcome. `busy`, `timeout`, `agent_error`, `blocked`, `task_unknown`,
`context_unknown`.

**`ErrorCode`** — the caller-visible union of both, for surfaces that render a
single failure to a user.

Obligations:

- A relay MUST set `origin: "relay"` on every error it originates, and MUST NOT
  originate a `PeerFailureCode`-only value.
- A relay MUST NOT distinguish "handle does not exist" from "handle exists but
  you may not reach it" in a way an unauthorized caller can observe. Both are
  `unknown_handle`.
- A caller MUST NOT retry `unauthorized`, `blocked`, `message_too_large`, or
  `protocol_error`. These are deterministic.
- A caller MAY retry `offline`, `busy`, `rate_limited`, and `timeout`, and
  SHOULD retry at most once before surfacing the failure.
- A refusal to answer is **not** an error code. Whether a reply may reach the
  caller is decided by clearance and reported inside the reply's own refusal
  reason.

## Limits

Normative values, defined in `packages/shared/src/protocol.ts`. An
implementation MUST enforce them and MUST NOT raise them per-caller.

| Limit | Constant |
|---|---|
| Calls per hour, per caller | `RATE_LIMIT_PER_HOUR` |
| Request message bytes | `MAX_MESSAGE_BYTES` |
| Reply bytes | `MAX_REPLY_BYTES` |
| Relay call timeout | `RELAY_CALL_TIMEOUT_MS` |
| Agent timeout | `AGENT_TIMEOUT_MS` |
| Durable execute window | `MAILBOX_TTL_MS` |
| Durable tombstone retention | `MAILBOX_TOMBSTONE_TTL_MS` |
| Queued tasks per callee | `MAILBOX_MAX_QUEUED_TASKS` |
| Outstanding per caller | `MAILBOX_MAX_OUTSTANDING_PER_CALLER` |
| Stored ciphertext bytes | `MAILBOX_MAX_STORED_CIPHERTEXT_BYTES` |
| Durable starts per day | `MAILBOX_MAX_STARTS_PER_DAY` |
| Context lifetime | `CONTEXT_TTL_MS` |
| Turns per context | `MAX_CONTEXT_TURNS` |

`scripts/spec-constants.test.mjs` fails the gate if this table names a constant
that no longer exists, or omits one that the protocol defines.

## Idempotency and replay

Scoped to durable delivery. Synchronous calls are correlated per-connection and
need no message identifier.

A durable request is identified by `(caller identity, message_id)`. Against that
key the relay MUST:

- return the existing receipt when the request envelope digest **matches** a
  known submission — a retry MUST NOT create a second call;
- reject with `protocol_error` when the digest **differs** — one `message_id`
  MUST NOT name two different requests.

**The guarantee is bounded, and callers must be able to reason about the
bound.** A submission is protected until `execute_by + MAILBOX_TOMBSTONE_TTL_MS`,
where `execute_by` is at most `MAILBOX_TTL_MS` after submission. After that the
identifier is released and the same `message_id` MAY be admitted as a new call.

Within the tombstone window the relay MUST retain the idempotency metadata after
the call is terminal, and MUST discard the stored ciphertext at that point — the
tombstone is metadata, not payload.

A caller retrying after a long outage MUST NOT assume its `message_id` is still
protected, and SHOULD mint a new one rather than risk a duplicate.

## Deployment choices, not protocol

The following are free for a self-hosted relay to change without breaking
conformance. A caller MUST NOT depend on them.

- Storage engine, and whether durable tasks survive relay restart.
- Keepalive cadence and idle-connection policy.
- Audit retention, export format, and destination.
- Rate-limit implementation, as long as the enforced ceiling is not raised.
- Registration and invite mechanics.
- Transport-level telemetry and sampling.

## What this version does not specify

Named so their absence is not read as permission:

- Agent Card contents and signing. See the A2A adoption designs; the card is
  currently specified only by its schema.
- Key publication, rotation, and the HPKE envelope construction. Specified in
  `packages/shared/src/e2ee.ts` and not yet restated normatively here.
- Registration, invites, and recovery credential exchange.
- The A2A task-store surface and its state mapping.
- Room and group semantics.
- Multi-turn context binding beyond the two limits in the table above.

Adding a section here is not a breaking change. Contradicting one is.
