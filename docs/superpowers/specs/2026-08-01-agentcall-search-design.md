# `agentcall search` — resolving *who* to ask

**Date:** 2026-08-01
**Status:** **Design, approved.** Ready for an implementation plan. Nothing built yet.
**Issue:** [#24](https://github.com/KenTaniguchi-R/agentcall/issues/24)
**Reviewed:** adversarially by Codex against the current tree; every file reference
below was verified, not asserted. Four claims in the first draft were false and are
corrected here (see "What the review killed").

## The problem

Every command assumes the caller already knows the address. `agentcall card
<address>` shows one person's task menu; `contacts.ts` shortens addresses you
already saved. Both start from "you know who to ask."

That does not survive a 500-person company, and it is the asker's half of the pain
the demand research named — *managers' #2 challenge is that the people with the
knowledge spend too much time answering questions.* The asker's half of that is not
knowing who knows.

**Discovery is a separate problem from calling, and only calling is built.**

Surfaced by [`docs/research/2026-07-31-lessons-from-composio.md`](../../research/2026-07-31-lessons-from-composio.md).
Composio has 1,000+ tools and loads **none** into context: `composio search "<task>"`
→ `composio execute <TOOL>`. The shape of our answer is the same, and so is the
first thing to get wrong — context bloat.

## Decisions

Six constraints, settled before the design:

| Question | Decision |
|---|---|
| What population does search span? | An **opt-in org roster** — not the whole relay, not just your contacts. |
| How does someone join one? | A **shared join secret**. |
| Where does matching happen? | **Client-side**, over a cached bundle. The query text never leaves the machine. |
| How much ships here? | **Explicit `search` only.** No SessionStart warm, no UserPromptSubmit routing. |
| How does ranking work? | **Lexical term-overlap** with an optional `keywords` field weighted higher. The calling LLM makes the semantic pick. |
| What does the bundle contain? | **Per-caller filtered** — each member's `default_offer` ∪ that member's grants to *you*. |

Rejected, with the reason:

- **Whole-relay search.** Registration is open (`apps/relay/src/index.ts:35`), so
  "any authenticated handle" is not a gate. It would also contradict the
  anti-enumeration stance already written into the relay.
- **Relay-side search endpoint.** The raw query — often more revealing than the call
  it leads to — would land in the operator's logs, cutting against #13 ("remove *the
  relay operator sees plaintext* from the security model").
- **Local-only search over contacts.** Zero new surface, but it only finds people you
  already know, which is not the problem #24 names.
- **Local embeddings.** Better recall on paraphrase, but it means bundling a model in
  a Node CLI, or an embedding API call that sends the query off-machine — the thing
  the client-side decision exists to prevent.

## Architecture

### Relay

New migration `apps/relay/migrations/0004_rosters.sql`:

```sql
CREATE TABLE rosters (
  id TEXT PRIMARY KEY,
  secret_hash TEXT NOT NULL,
  created_at INTEGER NOT NULL
);
CREATE TABLE roster_members (
  roster_id TEXT NOT NULL,
  handle TEXT NOT NULL,
  joined_at INTEGER NOT NULL,
  PRIMARY KEY (roster_id, handle)
);
CREATE INDEX roster_members_by_handle ON roster_members(handle);
```

There is no `owner_handle`. See "The honest tradeoff" below.

The roster `id` is relay-generated and opaque; **display names are local only**. On a
shared multi-tenant relay a global name like `acme` would be first-come-first-served
squattable and would imply an affiliation nothing verified. The `id` is unguessable
but not treated as a secret — it travels in URLs and will land in logs. The join
`secret` is a separate value, generated by the same 32-random-byte path as handle
tokens (`apps/relay/src/auth.ts:6`), stored only as a SHA-256 digest, and compared
with the existing constant-time helper (`apps/relay/src/auth.ts:11`). Neither the
secret nor the digest is ever logged.

Three endpoints. Every one authenticates first, and — where relevant — checks
membership **before** anything reveals that the roster exists.

**`POST /v1/roster`** — creates a roster, returns `{roster_id, secret}` exactly once.
Rate-limited on `REGISTER_RL` with a `roster:${handle}` key prefix, the same
distinct-prefix technique `/v1/token/rotate` already uses
(`apps/relay/src/index.ts:79`), so creating rosters costs the same as registering
handles and cannot be used to cheaply fill D1.

**`POST /v1/roster/:id/join`** — body carries the secret; on success writes a
membership row and the client discards the secret. Afterwards the handle token plus
the membership row is what authorizes.

- A new `ROSTER_RL` binding — added to the `ratelimits` array in
  `apps/relay/wrangler.jsonc` and to `Env` in `apps/relay/src/index.ts` — keyed by
  source IP *and* roster id. This is a credential-verification endpoint and must not
  share `READ_RL`'s 60/min read allowance (`apps/relay/wrangler.jsonc:28`).
- **Unknown roster and wrong secret return byte-identical 404s.** Anything else makes
  roster ids enumerable by probing.
- Correct secret against a roster at `MAX_ROSTER_MEMBERS` returns 409. Revealing
  existence there is fine — the caller already proved the secret.
- A repeat join by an existing member is idempotent: 200, no new row.

**`GET /v1/roster/:id/bundle`** — returns the per-caller filtered index.

- Non-member and unknown roster return byte-identical 404s.
- One bounded query, never N:

```sql
SELECT c.handle, c.card_json, c.updated_at
  FROM roster_members m JOIN cards c ON c.handle = m.handle
 WHERE m.roster_id = ?
```

- Filtering moves out of the route into a pure exported helper,
  `visibleTasks(upload, viewer)`, so the bundle and `GET /v1/card/:handle` cannot
  drift. **The helper carries the `Object.hasOwn` guard from
  `apps/relay/src/index.ts:145` with it** — a naive `upload.grants[viewer]` rewrite
  reintroduces the documented prototype-key failure, where a viewer handle of
  `constructor` returns the Object constructor and 500s the endpoint.
- **Members with zero visible tasks are omitted from `entries` entirely.** This is
  what actually makes them invisible; an entry carrying a handle and description
  still discloses membership. The endpoint is a search index, not an org directory.
- A stored card that fails to parse is skipped and counted in `skipped`, never a 500
  for the other 199 members.
- `Cache-Control: private, no-store` — the response varies by caller, so no shared
  cache is safe. An `ETag` over `(max updated_at, member count, caller handle)` makes
  an unchanged refresh a 304.

`GET /v1/card/:handle` is deliberately anonymous with *optional* auth
(`apps/relay/src/index.ts:128-138`) and is left exactly as it is. The bundle does not
reuse that route; it reuses the extracted filtering helper behind mandatory auth.

### Bounds

The bundle serves a **projection**, not full cards:

```
{ handle, agent_kind, tasks: [{ id, name, description, keywords }], updated_at, truncated }
```

- `examples` are dropped — up to 5KB per task, and they are display detail available
  from `agentcall card <address>` once you know who to look up.
- At most the first 10 tasks per member are indexed.
- `MAX_ROSTER_MEMBERS = 200`, enforced at join.

Worst case is then arithmetic rather than hope:
`200 × 10 × (id 64 + name 100 + description 1000 + keywords 800) ≈ 4MB`.

`MAX_BUNDLE_BYTES` is a **design ceiling asserted by test**, not a runtime check that
truncates a response. The caps that actually bind at runtime are `MAX_ROSTER_MEMBERS`
(at join) and `MAX_BUNDLE_TASKS_PER_CARD` (at projection); the test proves those two
keep the response under the ceiling. Raising `MAX_CARD_TASKS` or a field cap later
fails that test rather than quietly blowing the budget in production.

**No silent truncation.** An entry that lost tasks carries `truncated: true`, and
search prints `3 more tasks not indexed — see agentcall card <addr>`.

### Shared

`packages/shared` owns every shape both sides agree on, per `CLAUDE.md`:

- `CardTask` gains `keywords: z.array(z.string().min(1).max(40)).max(20).default([])`
  — bounded per-string like every neighbouring field. Unbounded keyword strings would
  amplify: 20 strings × 50 tasks × 200 members, re-sent on every refresh.
- New `RosterBundle`, plus the create and join request/response schemas. They live
  here rather than being cast locally in the relay or CLI.
- New `MAX_ROSTER_MEMBERS`, `MAX_BUNDLE_TASKS_PER_CARD`, `MAX_BUNDLE_BYTES`.

Cards stored before this change keep parsing because `.default([])` supplies the
missing field. (Zod's unknown-key stripping is a *separate* property — it is what
let `tier` be removed, per the comment at `packages/shared/src/card.ts:6` — and is
not the reason additions are safe.)

**`buildCardUpload` at `packages/cli/src/card.ts:43` currently maps only
`{id, name, description, examples}`.** It must destructure `keywords` too, or the
field ships and is never published.

### CLI

- `agentcall roster join <id> --secret=… --as acme` — records
  `{name, roster_id, relay}` locally.
- `agentcall roster list` — local only; there is no server list endpoint.
- `agentcall roster forget <name>` — drops the **local** record. It does not remove
  your membership row, and the help text says so.
- `agentcall search "<question>" [--roster <name>] [--limit N] [--json] [--offline]`

With no `--roster`, search covers **every joined roster**, refreshing each and
merging results into one ranking — scores are comparable because the scale is
absolute, not relative to a corpus. `--roster` narrows to one. Each result names the
roster it came from, and a roster that fails to refresh degrades on its own (per the
table below) without taking the others down.

New `rosterCacheFile` in `packages/cli/src/paths.ts` → `~/.agentcall/roster.json`,
mode `0600` under a `0700` directory, matching `saveConfig`/`saveContacts`, because
the bundle contains capabilities granted privately to you. Written temp-file-then-
rename so an interrupted refresh cannot manufacture a corrupt cache.

The ranker lives in a new `packages/cli/src/search.ts` as pure functions with no I/O
and no clock. Network stays in `api.ts` (`fetchRosterBundle`); rendering stays in the
command action in `index.ts`.

### Flow

```
agentcall roster join <id> --secret=… --as acme
   → membership row written; secret discarded

agentcall search "why did we pick this auth migration"
   ├─ cache fresh?  → no network at all
   ├─ stale?        → GET /v1/roster/<id>/bundle  (handle token; per-caller filtered; 304 if unchanged)
   ├─ rank() locally over (member, task) pairs
   └─ tanaka@agentcall.benree.tech  architecture-history
      agentcall call tanaka@agentcall.benree.tech --task architecture-history "<message>"
```

## The matcher

### Tokenization

Specified rather than implied, because determinism is what makes the ranker
testable: NFKC-normalize, lowercase, split on `/[^\p{L}\p{N}]+/u`, drop a small fixed
English stopword list, dedupe.

Splitting on non-alphanumerics means `architecture-history` yields `architecture` and
`history` — which matters because `TASK_ID_RE` is hyphenated
(`packages/shared/src/protocol.ts:4`) and so are most task names. Deduping query
terms means repeating a word cannot skew a result.

### Scoring

Presence-per-field, summed over unique query terms:

| Field | Weight |
|---|---|
| `keywords` | 3 |
| `name` | 2 |
| `description` | 1 |

`examples` are **not** indexed, because the bundle projection drops them (see
"Bounds"). That is a deliberate consequence, not an oversight: examples are
phrasing samples for a task you have already found, and at up to 5KB per task they
are the single largest thing the bundle would carry. If recall later proves too
weak without them, the fix is `keywords` — a field the callee controls, costing 40
bytes a term — not re-shipping 5KB of prose per task to every member.

- **Presence, not count** — a card cannot climb by repeating a term.
- **Cross-field accumulation is intended.** A term appearing in both `keywords` and
  the description scores in both. That is genuine corroborating evidence, not double
  counting.
- **No length normalization.** A longer description can only win by matching more
  *distinct* terms, which is a real signal.
- A pair needs at least one surviving term to appear at all.
- **Zero matches prints one line — `no match in roster acme` — and never a fallback
  list.** This is Composio's discipline ("no generic verbs, no static fallback, no
  aliases") and it is what keeps the tool from being muted within a week.
- Tie-break: score desc, then handle asc, then task id asc. Fully deterministic, so
  tests assert exact output.

### Output

Default top 5 (`--limit`), because the consumer is an LLM context window and not
loading 200 cards into it is the entire point:

```
tanaka@agentcall.benree.tech  architecture-history
  Why past architecture decisions were made — ADR context and migration rationale.
  matched: auth, migration (keywords) · migration (description)
  agentcall call tanaka@agentcall.benree.tech --task architecture-history "<message>"
```

The `matched:` line is deliberate: the calling agent makes the semantic choice, so it
needs to see *why* something ranked rather than trusting an opaque number. The
printed command uses the canonical flag ordering already emitted by `agentcall card`
(`packages/cli/src/index.ts:182`).

**Everything rendered from the bundle is sanitized at render time** — control and
format characters stripped, fields truncated — for the reason already written into
`packages/shared/src/protocol.ts:16-23`: callee-authored text landing on a caller's
terminal is escape-injection surface. Sanitizing at render rather than at parse keeps
the cache faithful to what the relay actually served.

`--json` emits:

```json
{ "query": "...",
  "rosters": [{ "name": "acme", "cache_age_seconds": 42, "stale": false }],
  "results": [{ "roster": "acme", "address": "...", "handle": "...", "task": "...",
                "name": "...", "description": "...", "score": 7, "matched": [...] }] }
```

`rosters` is a list, not a scalar, because the default is to search all of them and
each has its own freshness.

That is the agent-facing contract, and it is tested for shape and for containing no
escape sequences.

## Cache and failure policy

One file, a map keyed by local roster name. Each entry carries
`{relay, caller, roster_id, etag, fetched_at, entries, skipped}`.

**The `(relay, caller, roster_id)` triple is validated on read.** If any of the three
does not match current config, the entry is a miss and is refetched — never served.
`packages/cli/src/config.ts` supports alternate relays, and two relays can host the
same local roster name; without this check one local identity could read another's
privately-granted tasks.

TTL is 15 minutes. The ETag makes an unchanged refresh a 304.

Concurrency needs no lock: temp-file-then-rename is atomic, and two racing searches
both write valid snapshots — last writer wins, and both are correct bundles.

| Condition | Behavior |
|---|---|
| Cache fresh | Use it. No network at all. |
| Stale, refresh succeeds | Use the new bundle. |
| Stale, relay unreachable / 429 / 5xx | Serve stale, one stderr line naming the age; `cache_age_seconds` in `--json`. |
| Stale, relay returns **404** | **Fail closed.** Refuse to serve results; mark the entry revoked. |
| Cold cache, no network | Error naming the fix (`agentcall roster join`, or retry online). |
| Corrupt cache JSON | Rebuild, one stderr line. |
| `--offline` | Never refresh; serve cache, error if cold. |

The fail-open default is the **opposite** of the `PreToolUse` guard's stance, and that
is deliberate. The guard decides whether *code runs*; search decides what to *print*.
Failing closed here protects nothing — the relay still enforces membership on the
actual call and the callee's policy still enforces disclosure — while silently
deleting the feature. The 404 row is the one case where the relay is reporting that
your *access* changed, and serving stale results there would advertise people you can
no longer reach.

Corrupt cache rebuilds rather than throwing, unlike `loadContacts`
(`packages/cli/src/contacts.ts:33`), which throws by design. The distinction is that
the cache is derived data — losing it costs a refetch — while `contacts.json` is the
only copy of user data.

## The honest tradeoff

**There is no expel, no leave-on-relay, and no secret rotation.** A leaked join secret
means abandoning that roster and creating another; everyone who joined stays joined.

This is written down rather than dressed up because the alternative was worse. A
single `owner_handle` creates a dead-owner failure mode that this codebase makes
likely: `uninstall --purge` destroys local credentials (`packages/cli/src/index.ts:347`)
while the relay handle persists, handle release is deliberately unimplemented
(`apps/relay/src/index.ts:66`), and token rotation changes the credential, not the
handle. Purging the sole owner would leave a permanently unadministrable roster.

Shipping rotation *without* expulsion would have been worse still: it blocks future
joins and does nothing about anyone already inside, while sounding like remediation.

Membership lifecycle — expel, ownership, audit, teardown — is a deliberate follow-up
issue, not a gap that was missed.

## Two honesty clauses

- **Search results are hints, not authorization.** A grant revoked by a callee
  persists in your cache until the TTL expires; search may surface a task whose call
  is then denied by policy.
- **The query text never leaves your machine. Search *activity* is not private.** The
  relay learns that handle X refreshed roster Y at time T. "Client-side matching"
  should not be read as more than it is.

The bundle does tell you which capabilities were granted specifically to you — but
that is already observable through the authenticated extended card view for anyone
who knows the handle. It is bulk and automatic here, not a new class of disclosure.
You never receive grant records, grantee lists, or tasks granted to anyone else.

## Testing

TDD per `CLAUDE.md` — failing test first, no live network, `ws`/`fs` mocked.

### `packages/shared`

- `CardTask` round-trip with and without `keywords`; a card stored before this change
  parses, proving `.default([])` is the mechanism.
- A 41-character keyword rejects; a 21st keyword rejects.
- `RosterBundle` and the create/join schemas round-trip and reject.
- **The bounds arithmetic**: `MAX_ROSTER_MEMBERS × worst-case projected card ≤
  MAX_BUNDLE_BYTES`. Fails if a later change raises `MAX_CARD_TASKS` or a field cap
  without revisiting the ceiling.

### `apps/relay`

- Wrong secret and unknown roster produce **byte-identical** responses — asserted as
  equality, because the property is indistinguishability, not two separate 404s.
- Non-member bundle fetch is byte-identical to unknown-roster.
- Correct secret against a full roster → 409. Repeat join → idempotent 200.
- Two callers, one card: each sees `default_offer` ∪ their own grants, and a task
  granted to the other is absent.
- **A member with zero visible tasks is absent from `entries` entirely.**
- A member handle of `constructor` does not 500 the bundle.
- One malformed stored card is skipped and counted; other members are returned; 200.
- `If-None-Match` on an unchanged bundle → 304.
- Join consumes `ROSTER_RL`, not `READ_RL`; creation is limited under the `roster:`
  key prefix.

### `packages/cli`

- **The invented-token test**, from Composio's `test_reads_the_cache`: a fictitious
  colleague with a nonsense keyword must route, proving results come from cache
  *contents* and not from anything hardcoded.
- **Over-firing tests, written first.** Adapting Composio's parametrized bare-verb
  list to our vocabulary — "deploy the worker", "fix the auth bug", "run the
  migration" must not rank a card sharing only a stopword or a single generic term.
  This is the test class that decides whether the tool survives contact with users.
- Zero match → one line, no fallback list.
- Presence-not-count: a card repeating a term 50 times loses to one carrying it once
  in `keywords`.
- Weight ordering (`keywords` > `name` > `description`) and deterministic tie-break,
  asserted on exact output.
- Tokenizer: hyphen splitting, NFKC, query dedupe.
- Render: control characters stripped; `--json` free of escape sequences; the printed
  command uses `--task` before the message.
- Cache: identity mismatch refetches and never serves; corrupt rebuilds; 404 refuses;
  stale-plus-unreachable serves with a warning; `--offline` on a cold cache errors.
  Mode `0600` under `0700`. An interrupted write leaves the previous cache intact.
- **`buildCardUpload` publishes `keywords`** — otherwise the field ships dead.
- **A scope guard**: this feature registers no `SessionStart` and no
  `UserPromptSubmit` behavior. Same spirit as the exact-hook-set test the Composio
  research doc calls out — proactive routing cannot arrive without someone
  deliberately editing that assertion.

## What the review killed

Codex reviewed the first draft against the tree. Four claims were false:

1. **"Rotation + pruning is real remediation."** No pruning endpoint existed in the
   proposal, and no leave endpoint either. Rotation blocks future joins and does
   nothing about anyone already inside. Resolved by cutting the administration
   surface entirely and stating the tradeoff.
2. **"Zero-task members are invisible."** "Returns every member's card" and
   "invisible" are not equivalent — an entry with a handle and description discloses
   membership regardless of what the matcher does. Resolved by omitting them
   server-side.
3. **"The same `verifyHandleToken` gate as everything else."** `GET /v1/card/:handle`
   is deliberately anonymous with optional auth. Resolved by extracting a pure
   filtering helper instead of reusing the route.
4. **"Zod strips unknowns, so old cards keep parsing."** True, but the wrong
   mechanism — `.default([])` is what makes the addition safe.

And the load-bearing finding: **possession of a handle token is not a meaningful
gate**, because registration is open. Roster membership is the real authorization,
which is why membership is checked before the endpoint reveals that the roster
exists.

## Out of scope

Deliberately not in this spec, each a follow-up:

- SessionStart cache warming and the UserPromptSubmit proactive-routing hook — they
  build on the cache this ships, and the false-positive discipline alone is a spec's
  worth of work.
- Plugin distribution (`plugin.json`, `hooks.json`).
- Membership lifecycle: expel, ownership, transfer, audit export, roster teardown.
- Domain verification, which is what would make a roster name mean anything.
- A card-delete endpoint. An uninstalled agent leaves a stale searchable card today;
  that predates this design.
- Group-based policy (#26). Rosters scope *discovery*; groups scope *disclosure*.
  They are different axes and should not be conflated.
